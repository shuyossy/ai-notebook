# 要約

本セッションは、Microsoft Foundry（AI エージェントの開発・運用基盤）上で、本番環境のエージェントの実行記録（トレース）をもとに品質を継続的に改善していく「改善ループ」を、NTT DATA の事例とあわせて紹介したものである。

## 本番でエージェントがつまずくところ

- 誤回答：システム上は正常に動いており、事前の評価にも合格しているのに、エージェントが気付かれないまま間違った回答をする。
- 手作業のレビュー：トレースを人が1件ずつ読むか、コーディングエージェントに貼り付けて仕分けしている。この方法は、エージェントが数個に増えただけで回らなくなる。
- 見えないコスト：ツール呼び出しやスキル読み込みにかかるコストが把握できず、エージェントを動かし続ける価値があるか判断できない。

## 改善しないことのコストと、ツール不足の実態

- 各種調査の数字が紹介された。
  - 74%の組織が「不正確さ」を最重要の AI リスクに挙げている（McKinsey）。
  - 99%の組織が AI 関連リスクで損失を経験し、64%は100万ドルを超える損失を出している（EY）。
  - 約40%の組織が、AI エージェントの利用を縮小・廃止する見込みである（Gartner）。
  - 2025年の AI インシデント（AI が原因の事故・問題）は362件で、過去最多となった。
- また、61%の組織が「評価に合格した後に顧客向けの障害を起こした」と回答し、74%が主に人手による評価に頼っている。自動評価を信頼している組織は9%にとどまる。
- 登壇者は「エージェントは新入社員のように、フィードバックを受けて成長すべきだ」と述べた。改善ループがあれば、1人の専門家のフィードバックで全員が使うエージェントが改善され、すべての変更の効果が計測される。

## Foundry が提供する改善ループ

- 本番で動いているエージェントのトレースを材料にして、「問題を見つける → 直す → 直ったことを確かめる」を Foundry の中で繰り返し回す仕組みである。これまで人がスプレッドシートやトレースの目視で行っていた改善作業を置き換える。
- 従来のやり方とループの違いは次のとおりである。
  - 従来：ユーザーの苦情を待つ → 自分でプロンプトを打って再現する → トレースを1件ずつ読む → 直し方を推測して再デプロイする。直ったかどうかを判断する基準（ベースライン）がない。
  - ループ：専門家が「良い回答」の基準を決める → ツールが失敗を見つけて修正案を作る → 評価で効果を確かめてからリリースする。すべての変更が、ベースラインと比べて数値で測られる。
- ループは次の4段階で構成され、④が終わると①に戻って回し続ける。
- ① Establish：「良い回答」の基準を決める
  - 業務の専門家がトレースを見て良い／悪いを判定し、期待する出力やコメントを平易な言葉で書き込む（アノテーション）。この判断が、そのまま評価のテストケースになる。
  - 使う機能：トレースへのアノテーション、ルーブリック評価器（自社で決めた採点基準で品質・安全性を採点する機能）、評価とゴールデンデータセット（実際のトレースを、繰り返し使える正解付きのテストデータにする機能）
- ② Identify：どこが悪いかを見つける
  - 何千件ものトレースから、繰り返し起きている失敗を自動でグループ化し、重要度順に並べる。1回の実行を見ても分からない誤回答・コスト急増・応答遅延・危険な出力を、ユーザーが苦情を言う前に見つけられる。
  - 使う機能：Insights、外部のフレームワーク（LangChain／LangGraph／CrewAI など）で作ったエージェントのトレース取得
- ③ Optimize：直し方を作って試す
  - Agent Optimizer が、①のアノテーションや②の Insights の結果をもとにプロンプトやスキルの修正案を作り、評価にかけて比較する。どの案を採用して本番に出すかは人が選ぶ。
  - 使う機能：Insights から Agent Optimizer への連携、スキルとプロンプトの最適化、品質を落とさずにコストを下げる機能（コスト最適化、モデルルーター（質問に応じて適切なモデルを自動で選ぶ機能）、モデルのトレーニング）
- ④ Validate and repeat：良くなったか確かめ、繰り返す
  - 新バージョンをベースラインと比べてからリリースし、リリース後も本番の利用データの一部を抜き出して採点し続ける。成績の良かったバージョンが次のベースラインになり、次の問題を探す①に戻る。
  - 使う機能：本番での継続評価、GitHub Actions／Azure DevOps（CI/CD ツール）での評価結果に基づくリリース可否の判定（リリースゲート）
- 役割分担：業務の専門家は①で「良い」を定義し、開発者は②③で問題を見つけて直し、リーダーは④の比較結果をもとに「新バージョンが良くなったか、動かす価値があるか」を判断する。

## NTT DATA：PMO エージェントの改善事例

- Azure DevOps（タスク管理などを行う開発管理ツール）と Teams（Work IQ 経由）のデータから、進捗監視・リスク特定・レポート作成・フォローアップ提案を行う PMO（プロジェクト管理支援）エージェントを Foundry で開発した。最終判断はプロジェクトマネージャー／PMO が行う。
- 改善の手順は次のとおりである。
  - トレースと Insights で問題を診断する。
  - トレースから評価用のデータセットを作る（学習用90件・評価用30件）。
  - 重み付けした業務固有の品質基準14項目で、ルーブリック評価を行う。
  - Agent Optimizer で、システムプロンプトとスキルを最適化する。
- 改善例：タスクキー「ATLAS-TASK204」を、Azure DevOps 上のタスク番号（ワークアイテム ID）「204」と取り違えて失敗していた。最適化によって、タスクキーを正しいワークアイテムに対応付ける手順がプロンプトに追加された。その結果、正しい ID（21）を特定し、確認できない点は「未検証」と明示する回答になった。
- 品質スコアは68.6から83.3に向上した（+14.7ポイント）。
- 10か月の参照プロジェクトでの試算では、対象タスクの人手工数を907.3時間から364.7時間に削減できる（約60%削減）。NTT DATA には国内だけで2,000のプロジェクトがあり、展開した場合の効果は大きい。
- 学び：改善は「ビジネスにとっての品質」を定義することから始まる。今後も Microsoft と協業し、評価を軸にしたエージェント運用（AgentOps）を企業の業務に広げていく。

# 所感

- 本セッションの核心は「トレースを取る」から「トレースで改善を回す」への移行であり、そのための仕組み（アノテーション → Insights → Optimizer → 継続評価）が Foundry 上で一通りそろったという点にある。当行で AI エージェントを本番運用する場合も、トレースの取得だけで止めず、評価・改善・リリースのサイクルをどう回すかを最初から運用設計に含めておくべきだと感じた。
- NTT DATA の事例で最も参考になるのは、「業務にとっての品質」を定義してから最適化に入った点である。金融機関の業務エージェントには、正確さに加えて、根拠の明示、未確認事項の明示、権限外の操作をしないことなど、業務特有の要件があるはずである。評価基準づくりを業務部門と IT 部門が連携して進めることが、成功の鍵になると考えられる。
- Optimizer が出した変更はスキルやプロンプトの差分として確認でき、最終的に本番へ反映するかは人が決める設計になっている。GitHub Actions／Azure DevOps で評価結果によるリリースゲートをかけられる点も、統制の観点で参考になる。
