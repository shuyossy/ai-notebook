# 要約

本セッションは GitHub 社による講演であり、GitHub（ソースコードの管理・共有サービス）と GitHub Copilot（AI によるコーディング支援）を使った開発を前提としている。紹介された機能は主に「GitHub Advanced Security（GHAS）」という GitHub のセキュリティ機能群で、一部は無料、多くは有償のオプションである。

## AI でコード・脆弱性・悪用スピードが急増

- AI がコードを書くようになり、GitHub に登録されるコードの量が爆発的に増えた。コミット（コード変更の登録）は直近で74億件に達し、2026年のプッシュ（コードのアップロード）量は2024年と2025年の合計を上回る。
- コードが増えた分、セキュリティ上の欠陥（脆弱性）も増えた。Dependabot（使っている OSS の脆弱性を検知・更新する GitHub の機能）が出した「使っている OSS に脆弱性がある」という警告は、1四半期だけで新たに4億3,900万件にのぼる。
- 攻撃側も速くなっている。脆弱性が公表されてから実際に攻撃に使われるまでの期間は、2023〜24年には数か月あったが、今では約1日まで縮まった。

## 終わりの見えない「脆弱性パッチ競争」

- Microsoft CEO の Satya Nadella は、「AI が次々と見つけるバグに修正を当て続ける状況が、いつ終わるか分からない」と発言している。
- セキュリティ業界の見方は2つに分かれている。「厳しい1年を乗り切れば落ち着く」という見方と、「AI が賢くなり続ける限り、先は読めない」という見方である。

## GHAS のビジョンと本セッションの範囲

- GHAS が目指すのは、「AI が書いたコードでも人が書いたコードでも、特別な対策をしなくても最初から安全で高品質になっている」状態である。
- 開発の工程（コードを書く → テストする → 本番に出す）のうち、本セッションは「コードを書く」段階に絞り、次の3種類のリスクを扱った。
  - 取り込んでいる OSS の問題
  - 自分たちが書いたコードの欠陥
  - パスワードや API キーなどの「シークレット」がコードに紛れ込む問題

## OSS 依存関係：マルウェアの急増

- 2026年は、OSS に紛れ込んだ「マルウェア（悪意を持って作られたパッケージ）」の報告件数が、「脆弱性（正規パッケージのうっかりミス）」の約8倍（10.7万件 対 1.26万件）に急増した。
- 両者は対処法が違う。脆弱性は、修正済みの新しいバージョンに上げれば直る。一方マルウェアは、パッケージそのものを取り除く必要がある。典型的な手口は、有名パッケージに似た名前（例：lodash に対して「l0dash」）で打ち間違いを狙う「タイポスクワッティング」である。
- 急増の理由として、次の4つが挙げられた。
  - 悪意あるパッケージを公開するコストがほぼゼロである。
  - AI を使えば、本物そっくりの偽物を大量に作れる。
  - パッケージを自動でインストールする AI エージェントや、急いでいる人間が引っかかりやすい。
  - 防御側の発見能力が上がり、見つかる件数自体も増えた。

## 予防：パッケージファイアウォール（プレビュー）

- 開発者の PC・CI（ビルドやテストを自動で行う仕組み）・AI エージェントと、OSS の公開配布元（npm などのレジストリ）との間に置くファイアウォールである。パッケージをダウンロードするたびに検査し、社内ルールに反するものはインストールさせない。
- 止められるものは次のとおりである。
  - 既知のマルウェア
  - 一定以上の深刻度（CVSS という業界共通の点数）の脆弱性を持つパッケージ
  - 不審な変化があったバージョン（作成元の証明書（SLSA 来歴証明）が急に消えた、インストール時に自動実行されるスクリプトが新たに追加された、など）
  - 公開されたばかりのバージョン（数日間寝かせて、問題が見つかるのを待つ「クールダウン」の考え方）
- 社内で禁止しているライセンス（例：改変したコードにも同じライセンスでの公開を求めるコピーレフト）のパッケージを止めることもできる。
- 登壇者は「脆弱性の総量が激増している今、そもそも入れない予防が最も効く」と強調した。

## 検知：Dependabot マルウェアアラート

- すでに取り込んでいるパッケージにマルウェアが含まれていないかを監視し、見つかれば警告する機能である。リポジトリの設定画面でオンにするだけで、無料で使える。

## 優先順位付け：到達可能性分析

- 脆弱性の警告は大量に出るため、どれから直すかの判断が重要になる。
- 到達可能性分析は、「脆弱なパッケージを取り込んでいる」だけでなく、「自分たちのコードが実際にその危険な部分を呼び出しているか」をプログラムの解析で判定する。呼び出していなければ、実際の危険度は低い。
- 判定結果だけに頼らず、次の情報と組み合わせて優先順位を付けることが推奨された。
  - 深刻度（CVSS）
  - 実際に攻撃に使われる可能性の予測値（EPSS）
  - そのコードが本番環境で動いているか（Microsoft Defender for Cloud や JFrog などの外部製品と連携して判定）

## 修復：Dependabot 更新とエージェントへのアサイン

- 直し方は2通りある。
- 1つ目は、Dependabot に修正済みバージョンへ上げる変更（PR：コードの変更を取り込んでもらうための依頼）を自動で作らせる方法である。開発者はレビューして取り込むだけで済む。
- 2つ目は、AI エージェントに任せる方法である。バージョンを上げると他の部分が動かなくなる（互換性のない変更がある）ケースで使う。警告を AI エージェントに割り当てると、エージェントがリポジトリの内容を読んで、脆弱性の修正と動かなくなった部分の手直しをまとめて PR にする。エージェントは GitHub Copilot に限らず、Claude や Codex なども選べる。

## コードスキャン：同じバグ類型が新しい規模で

- ここからは、OSS ではなく「自分たちが書いたコード」の欠陥の話である。見つけるのは、GitHub の解析エンジン CodeQL と、AI による検査（AI スキャン）である。
- 見つかる欠陥の種類は、クロスサイトスクリプティング（XSS）や SSRF（サーバーに不正なリクエストを送らせる攻撃）など、昔からよく知られたものが中心である。変わったのは件数で、同じ種類の欠陥の報告が前年同期比で3.9倍に増えた（種類によっては8〜9倍）。
- そのため、コードが書かれるあらゆる場所、特に AI がコードを書く場所で、コードスキャンを常に動かすことが重要である。

## 予防：VS Code のセキュリティレビュー

- VS Code の GitHub Copilot に「/security-review」と指示すると、手元で書いたコードをコミットする前に、AI がセキュリティ上の問題をチェックする。
- SQL インジェクション、SSRF、XSS などの問題を、深刻度と「どれくらい確かか」の評価付きで一覧にしてくれる。そのまま AI に修正させることもできる。
- 問題のあるコードを、そもそもリポジトリに入れないための予防策という位置づけである。

## 検知：CodeQL と AI スキャン／修復：エージェンティック・オートフィックス

- リポジトリの設定で Code Security（有償）をオンにすると、CodeQL による自動解析で欠陥が検出される。
- CodeQL が対応していないプログラミング言語（PHP など）は、AI スキャンで補える。AI スキャンは、PR が作られるたびに AI がコードを検査する機能である。
- 検出された欠陥は、GitHub Copilot に割り当てると修正の PR を自動で作ってくれる（エージェンティック・オートフィックス）。

## シークレット保護の設定と検知

- 設定画面の「Secret Protection」をオンにすると、リポジトリを常時監視し、過去の履歴も含めてシークレットを見つけて警告する。
- 主な機能は次の3つである。
  - プッシュ保護：シークレットを含むアップロードをブロックする。
  - カスタムパターン：自社独自の形式の鍵を、文字列のパターン（正規表現）として登録して検出する。パターンは AI に作らせることもできる。
  - AI によるシークレット検出：決まった形式を持たないパスワードなども、AI が見つけ出す。
- 漏れたシークレットはどれも危険なため、優先順位を付けるより、すべて対応するのが基本である。

# 所感

- 「AI 活用でコード量が増える」ことと「セキュリティのバックログ（未対応の課題）が増える」ことはセットで起きる、という前提を再認識できるセッションだった。当行でも生成 AI によるコーディングを広げているところであり、同時並行で脆弱性の検知・対応の仕組みを整えておくべきだと感じた。
- OSS のマルウェアが脆弱性の8倍に達しているという点には驚いた。従来の SCA（使っている OSS の既知脆弱性の管理）だけでは不十分で、「悪意あるパッケージを入れない」仕組みが別に必要だと感じた。特に、依存関係を自律的にインストールするコーディングエージェントを使う場合は、パッケージファイアウォールのようなレジストリ側の関所（マルウェアのブロック、公開直後のバージョンのクールダウン、インストールスクリプト追加の検知）が有効だと考えられる。
- 一貫したメッセージは「後片付けより予防」である。プッシュ保護、パッケージファイアウォール、コミット前の /security-review といった流入を止める施策を先に打ち、残ったものを到達可能性で絞ってから直す、という順番は、脆弱性管理の方針として参考になりそうである。
- 修復の自動化は、エージェントに PR を作らせる段階まで来ている（Dependabot アラートやコードスキャンの指摘のエージェントへのアサイン、全件一括のオートフィックス）。ただし、生成された PR のレビュー体制や責任分界、AI クレジットの消費（コスト）をどう管理するかは、導入前に整理しておく必要がある。
