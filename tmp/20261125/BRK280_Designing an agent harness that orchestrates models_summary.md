# 要約

本セッションは、GitHub Copilot が複数の AI モデルを組み合わせてタスクを処理する仕組み「Copilot Fusion」について、その設計の考え方と性能を解説したものである。タイトルにある「エージェントハーネス」とは、AI モデルを動かしてタスクを進めるための周辺の仕組み（どのモデルに何をさせるかの制御など）を指す。

## 手作業のオーケストレーションから Copilot Fusion へ

- 「2つのモデルに同じ質問をして良い方を採る」「行き詰まったら大きいモデルに切り替える」といった、人が手作業で行っていたモデルの使い分け（オーケストレーション）を製品化したものである。
- Auto → HyDRA（2026年5月）→ Project HydraFusion（2026年夏、CLI でプレビュー）を経て、2026年10月28日（GitHub Universe）に GitHub Copilot Fusion として正式提供された。

## Terminal-Bench 4.1 で1位

- Terminal-Bench は、AI エージェントがターミナル（コマンド操作の画面）上の実務的なタスクをどれだけ解けるかを測るベンチマークである。
- Copilot Fusion Max が解決率71.2%で1位となった。Fable 5.2 と Claude Opus 5.5（いずれも65.8%）を5.4ポイント上回った。
- ベンチマーク全体の実行コストは約2,000ドルで、Fable 5.2（約16,500ドル）より88%、Opus 5.5 より57%低い。使用したトークン（AI が処理する文字量の単位）の量も79%少ない。

## Copilot Fusion の提供状況

- 対応クライアントは6種類である（VS Code、Copilot アプリ、Copilot CLI、JetBrains、Visual Studio、GitHub.com）。
- 組織で利用を制限しているモデルのポリシーは守られる。管理者は、使用するモデルの候補（モデルプール）と既定のエフォート（どれだけ手間をかけて処理するかの段階）を設定でき、Fusion を既定のモデルにすることもできる。

## 3つのエフォートレベル

- Standard：日常作業向け。プロンプトごとに1つのモデルを選ぶ。
- High：難しめのタスク向け。複数のモデルがチームとして動く（下書き＋レビュー）。
- Max：最も難しいタスク向け。最上位クラスのモデルでチームを組む（Terminal-Bench で1位になったのはこのモード）。

## なぜ1つのモデルでは不十分か

- Fable 5.2 は Opus 5.5 の3.5倍のコストがかかるが、スコアは同じ65.8%で頭打ちだった。モデルを大きくしても、品質の上限は上がらない。
- モデルごとに苦手な部分（死角）が異なるため、複数のモデルを協調させることで上限が上がる（71.2%）。

## Fusion の仕組みと3つのワークフロー

- 各プロンプトを「推論・コード生成・デバッグ・ツール利用」の4つの観点で採点し、基準を満たす最も単純なパターンを選ぶ。パターンは次の3つである。
  - Single：1つのモデルで完結する。
  - Cascade：低コストのモデルが下書きし、判定役（ジャッジ）が不十分と判断したときだけ、性能の高いモデルに1回だけ切り替える。
  - Critique：別系統（別のモデルファミリー）のモデルが読み取り専用で並列にレビューし、作成したモデルが1回だけ修正する。

## 速度とキャッシュヒット率

- タスクあたりの平均時間は36.1分で、Claude Code＋Opus 5.5 の約61分より約40%短い。キャッシュヒット率は97%で、比較対象の全エージェント中1位だった。
  - キャッシュ：一度 AI に渡した入力を再利用し、2回目以降の処理を安く速くする仕組み。ヒット率が高いほど、コストと時間を抑えられる。
- 簡単なステップは高速なモデルに任せ、性能の高いモデルは必要なときだけ使う。さらに、キャッシュが無駄にならない区切りでモデルを切り替えることで、この速度を実現している。

## マルチモデル・オーケストレーションの難しさ

- 「このリクエストを処理できる最も安いモデル」を決めるには、モデルの能力、エフォート、キャッシュ、コンテキストウィンドウ（一度に扱える入力の量）の4つを同時に考慮する必要がある。
- キャッシュはモデル（と推論レベル）ごとに紐づく。そのため、途中で安いモデルに切り替えると、それまでの会話全体をもう一度入力として支払うことになり、かえって高くつく場合がある。

# 所感

- 「どのモデルが最強か」ではなく、「どのタスクにどのモデルを、どう組み合わせるか」が品質とコストを左右する段階に入った。単一の最上位モデルに追従しておけばよいという方針は、コスト面でも品質面でも最適ではなくなりつつあると感じた。
- Cascade（安いモデルで下書き → ジャッジで判定 → 必要なときだけ切り替え）や Critique（別系統のモデルによる読み取り専用のレビュー）の考え方は、Copilot に限らず、自社で開発する AI アプリにも応用できそうである。
- コストはモデルの単価だけでは決まらず、キャッシュやコンテキストウィンドウの影響が大きいという点は、実運用で見落とされやすい。社内でエージェントを構築・評価する際は、トークン単価の比較だけでなく、キャッシュヒット率や長時間の利用、中断後の再開といった利用パターンも含めて試算すると、より精度が上がると考えられる。
