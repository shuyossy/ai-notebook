# 予実管理データ投入処理 性能見積りレポート

作成日: 2026-09-22

## 1. 結論

対象25,000件と今年度12ヶ月分の予実データ（約32.5万行）を **バルクINSERT（複数行VALUES・1トランザクション）** で投入する場合、処理時間は **一般的な環境で2〜5秒、公開ベンチマークの最も保守的な値でも約25秒** と見積もられ、30秒を超える懸念はない。

30秒を超えうるのは「1行ずつINSERTし都度コミットする方式」のみであり、本処理では採用しない。

## 2. 前提

| 項目 | 内容 |
|---|---|
| DB | PostgreSQL |
| 対象テーブル | 25,000行 |
| 予実テーブル | 25,000件 × 12ヶ月 = 300,000行（1行に当月の予算・実績を保持） |
| 合計投入行数 | 約325,000行 |
| 投入方式 | 複数行VALUESのバルクINSERT（500〜1,000行/文）、全体を1トランザクションでコミット |
| 投入順 | 対象テーブル → 予実テーブル（FK参照先は先に投入） |
| データ量 | 1行100〜200バイト想定で 約30〜65MB。ディスク・メモリ上の制約にはならない |

## 3. 根拠① PostgreSQL公式ドキュメント

PostgreSQL公式マニュアル「第14章 性能に関するヒント 14.4 データベースへのデータ投入」に、大量投入時の推奨事項が明記されている。

- **自動コミットの無効化**: 複数INSERTを使う場合はautocommitを切り、最後に1回だけコミットする。行ごとにコミットすると、PostgreSQLは追加される行ごとに多くの処理を行う。
- **COPYの利用**: COPYは大量行のロードに最適化されており、INSERTの連続より大幅にオーバーヘッドが少ない。COPYを使えない場合はPREPARE/EXECUTEでINSERTの解析・計画コストを削減する。
- **インデックス・外部キー**: 新規テーブルへの投入では、データ投入後にインデックスやFK制約を作成する方が速い。

出典: https://www.postgresql.org/docs/18/populate.html

→ 本処理の方式（1トランザクション・バルクINSERT）は公式推奨に沿っている。

## 4. 根拠② 公開ベンチマークの実測値

| 同上 | 同上 | COPY | 14秒 → 約70万行/秒 |
| 同上 | 同上 | 単行INSERT | 9,000秒 → 約1,100行/秒 |

## 5. 机上計算（325,000行）

| ケース | 採用スループット | 見積り時間 | 判定 |
|---|---|---|---|
| 標準（Cybertec バルクINSERT） | 20万行/秒 | 約1.6秒 | ○ |
| 保守的（Tiger Data ベースライン） | 10万行/秒 | 約3.3秒 | ○ |
| 保守的 × 安全率3倍 | 約3.3万行/秒 | 約10秒 | ○ |
| 最悪（tech-champion、JSONB含む重い行） | 13,900行/秒 | 約23秒 | ○（30秒以内） |
| 参考: 単行INSERT・都度コミット | 1,100〜3,700行/秒 | 90〜300秒 | × |

予実テーブルは数値列中心の軽い行であるため、実際は「標準」〜「保守的」のレンジに収まる見込み。最悪ケースは15列・JSONB含む行での値であり、本処理の下限として十分保守的。

## 6. 付随コストの確認

| 項目 | 影響 | 対応 |
|---|---|---|
| 外部キー制約 | 参照先（25,000行）にPKインデックスがあれば30万件のチェックは数秒以内 | 対象テーブルを先に投入 |
| インデックス | 1本あたり書き込み時間が概ね20〜50%増 | 数本であれば上記見積りの安全率内 |
| 行単位トリガー | 存在すると数倍に増加しうる | 事前に有無を確認 |
| WAL/fsync | 1トランザクションならコミット時1回のみ | 都度コミットを避ける |

## 7. 実装上の遵守事項

1. 全体を `BEGIN` 〜 `COMMIT` の1トランザクションで実行する（またはORMの自動コミットを無効化）
2. INSERTは500〜1,000行ずつのマルチ行VALUESにまとめる
3. 対象テーブル → 予実テーブルの順に投入する
4. 行単位トリガーが存在する場合は事前に確認する

以上により、本処理が30秒を超えないことは公式推奨と公開実測値の両面から合理的に説明できる。
